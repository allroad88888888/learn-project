# 问题过滤——问负责人什么、怎么问

负责人的时间是整个环里最稀缺的资源。参考跑里，30 条原始问题去重后 22 条，其中真正改变新代码
去向的只有约四分之一。两条被弹回「没明白」，一条被弹回「看代码」。于是有下面的规则。

## 全部满足才问
1. **两种解释从代码看都通**——你确实分不出来。
2. **答案改变新代码放哪或怎么写**（哪个汇合点、什么形状、什么 API、某个写法能不能模仿）。
   纯观感或性能债不算——记进线文件的「已知债」，不问。
3. **代码答不了。** 「两份列表哪份是权威」grep 一下谁消费就知道。负责人会（正确地）弹回来。

## 怎么措辞
- **点名成员和文件**（「`editLogic.ts` 缺的 4 个是 `a, b, c, d`」），不说「有些成员」。
- **一问一事。** 别把「每个 X 是不是组件」和「这个循环是不是故意的」捆一句。
- **两种解释各一句**，都写成陈述句，让负责人挑。
- **允许非二元回答**：A / B / **都有** / 就这样 / 遗留 / 不知道 / 自由文本。自由文本是最好的回答
  （「现在全量打包；后续接线上」）——留位置。
- 合并前每线 ≤5；跨线去重（同一事实三条线各看到一次 = 一条问题、三个出处）。
- 合并清单分组：A 机制 · B 边界 · C 声明/标签 · D 遗留候选（留/删/不知道）· E 文档 vs 代码（不需裁，只需修）。

## 坏问题（来自参考跑）与原因
- 「`rootId` 硬编码是有意的吗？」——真缺陷，但不改变新代码去向 → 记已知债，不问。
- 「两份硬编码列表哪份权威？」——grep 消费者就知道；实际是两份不同用途的列表。
- 「hooks-in-map 是有意的，还是每个 logic 该各成一个组件？」——一句两问、成员没点名；负责人答「没明白」。

## 回答词汇及其后果
| 回答 | 线文件里的后果 |
|---|---|
| A / B / 都有 | 选中的解释成为陈述；另一种删掉或标错 |
| 就这样 | 升格为「已确认设计」；新代码照它 |
| 遗留 | 标「别模仿」；**不**安排删除，除非负责人说删 |
| 不知道 | 保持未决；注明「不是负责人的决定 / 另有作者」；按多数做法 |
| 自由文本 | 原文引进「裁决」；通常同时给出现状和方向 |
